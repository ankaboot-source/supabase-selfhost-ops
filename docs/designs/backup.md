# Design: Automated Backups + PITR with pgBackRest

> Issue: #118 — `feat(backup): automated backups + PITR with pgBackRest`
>
> **Status note (post-implementation):** the topology below describes the *original* design (sibling `supabase-pgbackrest` container). The shipped implementation superseded it — pgBackRest now runs **inside `supabase-db`** (binary + libs bind-mounted, `LD_LIBRARY_PATH` scoped by a wrapper), no shared PGDATA volume. See `AGENTS.md` → "Backup / pgBackRest" for the pitfalls and the "Weaknesses & Best Options" section for why the final approach was chosen.

## Goal

Give `ansible-supabase` a default-on backup story: a Postgres that backs itself up, is restorable to any point in time, and whose restore is verified automatically. Zero manual wiring for the Sunday self-hoster; a handful of var overrides for production.

## Non-goals (later layers)

- HA / streaming replication / automatic failover
- Multi-region or multi-target repo
- Granular (per-table) restore
- Advanced at-rest key rotation
- Backup of Realtime / Analytics state

## Topology

```
┌─────────────────────────────────────────────────────────────┐
│  Host                                                        │
│                                                              │
│  ┌──────────────────┐        ┌──────────────────────────┐   │
│  │  supabase-db     │        │  supabase-pgbackrest      │   │
│  │  (postgres:17)   │        │  (woblerr/pgbackrest)     │   │
│  │                  │        │                           │   │
│  │  PGDATA ─────────┼────────┼── PGDATA (shared volume)  │   │
│  │  archive_command │        │  stanza-create            │   │
│  │  = pgbackrest    │        │  backup / expire / verify │   │
│  │    archive-push  │        │  exporter :9854           │   │
│  │  (binary mounted │        │                           │   │
│  │   read-only)     │        │                           │   │
│  └──────────────────┘        └──────────────┬────────────┘   │
│                                             │                 │
│  ┌──────────────────────────────────────────▼─────────────┐  │
│  │  Backup repo (one of)                                  │  │
│  │  • rustfs (local, default)  • s3 (external)  • posix   │  │
│  └────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

### Why a sibling container (not a fork of `supabase/postgres`)

- Keeps us decoupled from Supabase's image — no rebuild on every upstream bump.
- pgBackRest has no official Docker image; `woblerr/pgbackrest:2.58.0-alpine` is the de-facto community image (UID/GID 2001).
- Both containers share the PGDATA volume at the same mount path (`/var/lib/postgresql/data`), so `%p` in `archive_command` resolves identically in both.

### `archive_command` approach

```
archive_command = 'pgbackrest --stanza=main archive-push %p'
```

The pgbackrest binary is bind-mounted read-only from the `woblerr/pgbackrest` image into the `db` container. Both containers are Alpine-based (musl libc, x86_64), so the binary is directly compatible. pgBackRest uses `archive-async=y` with its own internal spool for queueing and retry — no docker socket dependency, no custom archiver script. The pgbackrest sibling container runs the default entrypoint and handles on-demand backups, stanza management, and repo access.

Trade-off: the db container holds the pgbackrest config (with repo credentials) and needs network egress to the repo. This is a notch below TLS server mode (where creds stay on the sibling) but nowhere near docker.sock. TLS mode is the clean v2 if we want creds off the db container.

## Repo types

| `backup_repo_type` | What it is | Encryption | Warning |
|---|---|---|---|
| `rustfs` (default) | Local RustFS container on the same box, bound to `127.0.0.1:9000/9001` | off | **Loud warning**: same machine = same fate. No off-box protection. |
| `s3` | External S3-compatible (AWS S3, R2, B2, Wasabi) | **on** (forced) | None — off-box is the point. |
| `posix` | Local filesystem path | off | Same loud warning as `rustfs`. |

Encryption uses `repo1-cipher-type=aes-256-cbc` + `repo1-cipher-pass`. For external repos the passphrase is generated by `setup.sh` and the user is told to back it up elsewhere (if lost, the repo is unrecoverable). For local repos encryption is off — handing a beginner a key they'll lose is worse than no encryption on a box they already control.

## Retention defaults (hobby-safe)

| Variable | Default | Hardened |
|---|---|---|
| `backup_retention_full` | `3` | `7` |
| `backup_retention_diff` | `3` | `3` |
| `backup_retention_archive` | `3` | `7` |
| `backup_retention_archive_type` | `full` | `full` |

Effective PITR window ≈ `min(retention_archive, retention_full)` full-backup cycles: ≈3 days default, ≈7 days hardened (with weekly fulls + daily diffs).

## Schedules

| Schedule | Default cron | What it runs |
|---|---|---|
| Full backup | `0 3 * * 1` (Mon 03:00) | `pgbackrest backup --type=full` |
| Differential backup | `0 3 * * 2-7` (Tue–Sun 03:00) | `pgbackrest backup --type=diff` |
| Verify (integrity) | `0 4 * * *` (daily 04:00) | `pgbackrest verify` |
| Restore drill | off (`backup_restore_drill: false`) | full restore into throwaway volume + healthchecks |

## Credentials

| `backup_creds_source` | Behavior | Warning |
|---|---|---|
| `.env` (default) | S3 keys / local store creds rendered into the backup compose `.env` file | Warned: plaintext on the box |
| `vault` | Ansible Vault variables consumed directly by the role | None — the hardened path |

## pgsodium key backup

The `db-config` Docker named volume holds `/etc/postgresql-custom/pgsodium_root.key` (32-byte root key). Without it, every `vault.secret` and every pgsodium-encrypted column is unrecoverable. The role:

1. `docker compose run --rm db cat /etc/postgresql-custom/pgsodium_root.key > {{ backup_dir }}/pgsodium_root.key`
2. Also backs up `/etc/postgresql-custom/conf.d/` (custom GUCs).
3. On restore, writes the key back to the `db-config` volume **before** starting the db, chown `postgres:postgres`, chmod `600`.

## Storage volume backup

Detect the backend first: if Storage is on external S3 (`STORAGE_BACKEND=s3`), the volume backup is meaningless and is skipped. If `STORAGE_BACKEND=file`, the role tars `./volumes/storage/` into the backup repo. The storage/DB restore inconsistency window (storage.objects rows in PG vs bytes in the volume, backed up at different times) is documented.

## Prometheus metrics + Grafana + alerting

- `woblerr/pgbackrest_exporter:2.55.1` container on `127.0.0.1:9854`, scraped by the existing Prometheus (new scrape target added to `prometheus.yml.j2` when `backup_enabled`).
- Grafana panel: `pgbackrest_stanza_status` (0=ok), `pgbackrest_backup_last_full_timestamp_seconds` (age = `time() - ...`), `pgbackrest_wal_archive_min/max`, `pgbackrest_backup_last_error`.
- Alerts (always on, regardless of config):
  - `pgbackrest_stanza_status > 0` (archive/backup problem)
  - `time() - pgbackrest_backup_last_full_timestamp_seconds > 25h` (missed/failed scheduled run)
  - `pgbackrest_wal_archive_max - pgbackrest_wal_archive_min` growing (archive lag)
  - `pgbackrest_backup_last_error > 0` (last backup errored)
  - node-exporter `pg_wal` disk usage rising (via existing node-exporter filesystem collector on the PGDATA path)

## Restore playbooks

### `restore.yml` (PITR, destructive)

```
ansible-playbook restore.yml -e "target_time='2026-08-01 12:30:00+00'"
```

Guardrails (issue §D):
1. Refuses to run without `target_time` set (no accidental "restore to now").
2. Requires explicit confirmation: prints the target time + current time + warns it will overwrite PGDATA, waits for `yes`/`no`.
3. Takes a fresh full backup of current state **before** overwriting (last-chance snapshot).
4. Stops `supabase-db`, runs `pgbackrest --stanza=main --type=time --target=... --target-action=promote --delta restore`, restarts db.
5. Waits for Supabase services (Auth, Storage, PostgREST) to respond healthy.

### `restore-verify.yml` (non-destructive, opt-in)

Restores into a throwaway volume + starts a read-only Postgres on a side port + runs healthchecks. Never touches prod. Off by default (`backup_restore_drill: false`); resource warning printed when enabled.

### `backup.yml` (on-demand)

Runs a full backup immediately. Useful before risky migrations.

## Idempotency

- `stanza-create` is idempotent (pgBackRest skips existing stanzas, returns success).
- Re-running the role does **not** re-init the stanza or expire backups.
- `stanza-upgrade` is the one exception — required after a PG major version upgrade (PG 15→17). Pre-upgrade backups are **not** restorable into the new cluster. The upgrade playbook (separate issue) must take a fresh full backup and re-baseline the stanza immediately post-upgrade.

## Config flow

New `advanced.backup` fields in `config.example.yml` → `setup.sh` reads via `cfg_get`/`cfg_bool` → renders to `env/supabase.yml` via `set_env_var` → consumed by the `backup` role. The old S3-dump backup config fields are removed.
